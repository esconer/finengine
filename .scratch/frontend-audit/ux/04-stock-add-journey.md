# 04 — Flagship Cash-Equity Journey: Discover → Research → Assess → Add

**Status:** design/specification only; no product code changed.  
**Date:** 2026-09-24.  
**Scope:** listed cash equities only (India-first, with the current global fallback seams); no futures, options, order routing, tax, brokerage, or trade execution.

> **Truth rule for this document**
>
> - `Current` means the behavior is present in the inspected production code and is cited.
> - `Proposed` means a contract, policy, or new backend capability that does **not** exist yet.
> - `null`/`N/A` means unavailable. It must never be converted to `0`, “flat,” “neutral,” or a fabricated delta.
> - The threshold numbers in §5 are an explicit **proposed Balanced policy preset**, not values returned by the current backend. The backend must own and echo the approved policy; the client must not silently invent a fallback policy.
> - “Live” in the UI means a successful server request to the configured vendor/cache cascade. FinEngine does not currently claim exchange-real-time entitlement; quote timestamps are generated by the data service (`backend/app/services/data_service.py:695-718`, `:741-756`).

---

## 1. Executive design decision

Make the flagship journey **research-first and impact-gated**, not another one-click “add” button:

1. **Discover** a candidate from the existing Screener Studio or by validating a ticker.
2. **Research by user question**: what am I buying, how is the business doing, what am I paying for, what happened to price, what is momentum/volatility saying, what can hurt, and who owns it.
3. **Assess “What if I add this?”** with a server-computed, non-mutating before/after view. The candidate amount is explicit; the funding assumption is explicit.
4. **Review** the exact post-add weights, risk deltas, exposures, liquidity, source/as-of, and policy verdict.
5. **Commit** only after a second server response confirms `POST /portfolio/add` succeeded. The impact request never writes a position.

The current product already has most research primitives and a correct create-position route, but it does **not** have a coherent candidate-impact request/response. The proposed orchestration endpoint below is therefore a design boundary, not a claim that a route exists.

## 3. Step 1 — Discover and identify the ticker

### 3.1 Discovery surfaces

#### A. Screener Studio (recommended first entry)

The current screener has five India-focused bfinance strategies and a custom screen (`backend/app/services/screener_service.py:63-103`, `:180-268`). Each `ScreenerStock` currently carries only the screening snapshot fields (`frontend/src/types/index.ts:594-605`); it is not a research or impact response.

Target row actions:

- **Research** — existing `/dashboard/equity-research?ticker={ticker}` deep link.
- **Assess add** — open a draft assessment for this ticker; do not call `portfolioApi.addPosition`.
- **Add** — only after the assessment and review are complete. The current one-click path at `screener-studio/page.tsx:163-185` is not the flagship action.

The current table search is a client-side filter over loaded results (`screener-studio/page.tsx:638-647`). It is not a global fuzzy-search service. The UI must not imply that a no-match search queried a nonexistent backend index.

#### B. Direct ticker search

The current research input submits a ticker directly (`equity-research/page.tsx:161-165`) and the backend exposes `POST /data/validate` (`backend/app/api/data.py:540-558`; frontend wrapper at `frontend/src/lib/api.ts:261-265`). Use that route for identity validation, then load the research profile. Do not call the screener endpoint as a substitute for a direct ticker lookup.

Recommended behavior:

1. Trim and uppercase input; preserve exchange suffixes (`.NS`, `.BO`) and alphanumeric/hyphen scrip formats.
2. Call the existing validation route.
3. If valid, navigate to `?ticker={canonicalTicker}` and start the research state machine.
4. If invalid, retain the query and show the server’s message/suggestions; do not show the previous company.

### 3.2 Identity card

The first card answers “what exactly am I looking at?” and should contain only server-returned values:

- canonical ticker and company name;
- exchange/listing region;
- native quote currency and the portfolio base currency;
- current price, volume, market cap when present;
- sector/industry when present;
- 52-week range when present;
- provider used, latest bar/quote timestamp, and freshness status.

`DataService.fetch_quote` returns price, volume, market cap, sector, industry, 52-week fields, currency, exchange, source, and a generated timestamp (`backend/app/services/data_service.py:671-799`). The quote route is `GET /api/v1/data/quote/{ticker}` (`backend/app/api/data.py:462-485`). The current frontend wrapper declares only a narrow price/sector/company shape (`frontend/src/lib/api.ts:244-247`), so the new typed contract must preserve the additional fields or deliberately mark them unavailable.

**Formatting:** `.NS`/`.BO` values use `₹` and `en-IN`; the existing shared formatter uses `Intl.NumberFormat('en-IN')` and has a separate Cr/L helper (`frontend/src/lib/utils.ts:23-45`, `:87-100`). Never format an Indian price with a hard-coded `$` default.

### 3.3 No-result state

**Trigger:** invalid format, validation 404, screen result absent, or provider reports unknown ticker.

**UI:**

- Heading: “No listed ticker found.”
- Echo the submitted query and canonicalization rule.
- Show the backend detail/suggestions if present.
- Offer: **Try another ticker**, **Open Screener Studio**, and **Retry validation**.
- Keep the query in the URL/input so the user can correct it.
- Clear all candidate-specific data before rendering the empty state.

**Forbidden:** old company profile, old chart, a zero price, or “No data available” when the request actually failed.

## 4. Step 2 — Research by user question

The current research page is organized around API-era tabs (`Overview`, `Shareholding`, `Concalls`, `Statements`, `AI Dossier`) at `equity-research/page.tsx:550-580`. The target keeps the same data sources but changes the navigation to the questions a person asks before adding a holding.

Each section has three layers:

1. **Answer:** the smallest set of live fields needed to answer the question.
2. **Evidence:** period/as-of/provider/source and methodology.
3. **Availability:** available, missing, stale, or provider-degraded; never a silent empty state.

### 4.1 “What am I buying?” — identity, quote, business description

**Content:** company name, ticker, exchange, currency, sector taxonomy, indices, current price, market cap, 52-week range, about text, website, and provider/freshness.

**Current evidence:** profile route and schema at `backend/app/api/equity_research.py:37-53` and `backend/app/models/schemas.py:478-516`; quote cascade at `backend/app/services/data_service.py:695-799`.

**UI rule:** the price is a quote snapshot, not a promise of an executable price. Put the source and “as of” beside it. Do not call it “real-time exchange” unless a future licensed feed actually provides that entitlement.

### 4.2 “How is the business doing?” — fundamentals and financial health

**Content:**

- ROCE, ROE, margins, leverage, liquidity ratios, free cash flow;
- revenue/earnings/CAGR trend;
- income, balance-sheet, and cash-flow periods;
- peer rows when the current profile provides them.

**Current evidence:** curated fundamentals route at `backend/app/api/data.py:164-184`; field map and vendor cascade at `backend/app/services/company_data_service.py:81-112`, `:146-275`; statements route/service at `backend/app/api/data.py:187-205` and `company_data_service.py:285-365`. The research page already lazy-loads statements on tab entry (`frontend/src/app/dashboard/equity-research/page.tsx:130-149`).

**UI rule:** show the reporting period and source. A missing ratio is `N/A`; do not interpret a missing D/E or Piotroski score as zero. The current equity-research service itself contains `or 0` fallbacks for some custom ratios (`backend/app/services/equity_research_service.py:52-65`, `:226-243`), so the new contract should normalize nulls at the boundary and mark those fields informational/non-gating.

### 4.3 “What am I paying for?” — valuation and forensic context

**Content:** P/E, book value, price-to-book/PEG where available, dividend yield, Graham number/upside, EV/EBITDA, interest coverage, CFO/PAT, Piotroski F-score, peer comparison, credit rating/annual-report links.

**Current evidence:** custom ratios route at `backend/app/api/equity_research.py:89-104`; service assembly and Graham calculation at `backend/app/services/equity_research_service.py:213-257`; full-profile fields at `:72-116`; frontend type shape at `frontend/src/types/index.ts:521-529`.

**UI rule:** label these “reported/forensic ratios,” not a DCF, price target, or recommendation. No forward earnings, consensus target, or expected return may be inferred from them. If the current ratio service returns an upstream zero, the new contract must expose missingness rather than present a synthetic score.

### 4.4 “What happened to the price?” — history and drawdown

**Content:** adjusted-close price line, raw close/OHLCV on demand, volume, 52-week range, rolling drawdown, monthly returns, and benchmark comparison when a valid benchmark exists.

**Current evidence:** OHLCV route and source/cache envelope at `backend/app/api/data.py:365-453`; schema at `backend/app/models/schemas.py:127-137`; service fetch/storage/cascade at `backend/app/services/data_service.py:482-642`. The frontend currently declares `getStockData` as `Promise<StockData[]>` and returns the raw Axios data (`frontend/src/lib/api.ts:235-242`), while the backend response is an object containing `data`, `source`, `from_cache`, and `metadata`. This is a contract handoff item, not something to paper over in a chart component.

**UI rule:** label the chart “historical price data,” show the source and latest bar, and distinguish raw close from adjusted close. Do not imply that a cached frame is a live quote.

### 4.5 “What is momentum/volatility saying?” — technicals

**Content:** latest verified snapshot, SMA/EMA, MACD, RSI, Bollinger bands, ATR, VWMA, and MFI, with lookback window and warm-up disclosure.

**Current evidence:** technical route and stale/verified-snapshot routes at `backend/app/api/data.py:99-161`; supported indicators and descriptions at `backend/app/services/indicators_service.py:28-53`; stale guard at `:97-114`; computed records and `null` indicator values at `:161-208`. The current frontend API client has no indicator or verified-snapshot method (`frontend/src/lib/api.ts:232-305`), so this is a typed API handoff.

**UI rule:** technical indicators are descriptive observations, not a buy/sell signal. If the latest OHLCV row is more than the service’s `MAX_STALE_DAYS` threshold behind the requested end, show **Stale market data** and do not silently calculate a confident signal. The current service raises `StaleMarketDataError`; the data route maps it to HTTP 409 (`backend/app/api/data.py:127-133`, `:155-161`).

### 4.6 “What could hurt the portfolio?” — standalone risk

**Content:** annualized volatility, Sharpe/Sortino, historical max drawdown, historical 95% VaR/CVaR, skew/kurtosis, beta/R² where benchmark history is valid, tail dependence, stress scenarios, and current standalone liquidity.

**Current evidence:** realized-risk route at `backend/app/api/analytics.py:378-610`; forecast route at `:617-753`; engine metrics at `backend/app/services/analytics_engine.py:37-106`, `:891-973`; factor regression at `:1218-1343`; tail route at `backend/app/api/analytics.py:2385-2447` and tail service at `backend/app/services/tail_risk_service.py:17-73`.

**UI rule:** do not mix a current portfolio endpoint with a candidate endpoint unless both declare the same return convention, window, base currency, and estimator. Forecast risk is a separate model and may be unavailable; the first add-impact verdict should use historical observed metrics rather than a failed-model fallback. The current forecast engine has model-specific empty/null paths (`backend/app/services/analytics_engine.py:1054-1111`, `:1365-1377`).

### 4.7 “Who owns and controls it?” — ownership and governance

**Content:** quarterly/yearly promoter, FII/FPI, DII, government, and public holdings; promoter holding/pledge; insider transactions; reporting period and source.

**Current evidence:** India shareholding route at `backend/app/api/equity_research.py:56-70`; service at `backend/app/services/equity_research_service.py:126-191`; profile promoter fields at `:98-106`; insider route at `backend/app/api/data.py:208-216` and normalization at `backend/app/services/company_data_service.py:369-393`.

**UI rule:** say “India institutional/shareholding pattern” rather than implying global ownership coverage. There is no current US ownership route in the inspected API inventory. A missing ownership series is not neutral ownership and cannot affect the portfolio verdict unless the user explicitly makes it a policy gate.

### 4.8 Research items that must not be invented

There is no current news/sentiment, analyst-estimate, recommendation, or target-price route in `backend/app/api/data.py:99-216` or `backend/app/api/equity_research.py:37-193`, and no such service in `company_data_service.py`. The first journey may show a small “Not available in current research contract” disclosure; it must not show sentiment `0`, a fake neutral consensus, or a fabricated target price.

## 5. Step 3 — “What if I add this?” decision analysis

### 5.1 The non-negotiable separation

The impact analysis is **read-only**. It must not call `POST /portfolio/add`, mutate a position, or infer a sell. The current rebalance route cannot be used for a new candidate: it rejects unknown tickers (`backend/app/api/portfolio.py:1083-1095`) and operates on current positions only. Its dry-run response is an order simulation, not a candidate add-impact response (`backend/app/api/portfolio.py:1160-1170`).

### 5.2 Funding semantics

The current database stores risky positions but no cash ledger (`backend/app/models/database.py:23-45`). Therefore the first honest journey uses:

> **External cash (hypothetical):** the user states how much new cash they intend to deploy. FinEngine shows the hypothetical post-add risky weights; it does not claim that this cash exists in the database.

Let:

- `P` = current risky portfolio market value in the selected base currency;
- `V_i` = current holding value;
- `A` = explicit proposed candidate amount;
- `w_before` = current market-value weights;
- `w_after` = hypothetical post-add weights.

For external cash:

```text
w_before[i] = V_i / P
w_after[i]  = V_i / (P + A)       for existing holdings
w_after[X]  = A / (P + A)         for the candidate
```

`P`, `V_i`, `A`, base currency, and the resulting weights must be returned by the backend. The client may preview a value while the request is pending, but the review is invalid until the server response reconciles weights to a tolerance and returns its funding basis.

**Empty portfolio:** when `P = 0`, the first candidate is the only risky holding: post weight is exactly `1.0`, HHI is `1.0`, effective N is `1.0`, and diversification score is `0%`. This is a bootstrap fact, not a quality verdict. Never manufacture a portfolio total such as `100000` to make the math look populated; the existing modal correctly gates the zero-state calculation on a successful portfolio fetch (`frontend/src/components/portfolio/AddPositionModalSimple.tsx:40-93`).

**Already-held candidate:** the current add route returns 409 for an existing canonical ticker (`backend/app/api/portfolio.py:372-380`). The journey must show “Already held — review a top-up/update,” not repeatedly submit a create request. A true top-up impact calculation and its mutation contract are a backend gap; the current `PUT /portfolio/{ticker}` route exists for ordinary position updates (`backend/app/api/portfolio.py:817-895`), but it is not a candidate-add contract.

### 5.3 Return, currency, and freshness convention

All before/after calculations use the same candidate amount, return frame, dates, base currency, FX series, and estimator. A new endpoint/service must return those choices in the response.

Basic design convention:

- adjusted-close daily simple returns;
- local-currency returns converted to the base currency only when a live, supported FX observation exists;
- one documented calendar-alignment policy;
- a requested window with a minimum of 252 aligned sessions for annualized covariance/risk deltas;
- positive raw and adjusted prices for every leg;
- 30 positive-volume sessions for liquidity.

This is stricter than a current route’s ad-hoc equal-weight fallback. `resolve_allocation` currently equal-weights non-DB tickers (`backend/app/api/analytics.py:235-265`); that behavior is useful for a research screen but is not a candidate valuation.

The current currency service supports only INR/USD (`backend/app/services/currency_service.py:25-27`, `:86-93`) and can return a marked fallback constant when the live vendor is unavailable (`:135-169`, `:249-287`). Mixed-currency impact must show the FX provenance and block a ship-first verdict when the rate is fallback. The portfolio route itself rejects currencies outside INR/USD (`backend/app/api/portfolio.py:42-80`).

### 5.4 Metric contract and backend capability matrix

Status vocabulary:

- **Service exists / endpoint exists:** the current route returns the current portfolio value or current-universe measurement.
- **Service exists / add delta missing:** all numerical ingredients exist, but no current endpoint freezes a funding assumption and returns coherent before/after values.
- **New service or endpoint required:** the current service does not expose the needed primitive or a safe candidate-aware contract.
- **Context only:** a research value that must not silently become a decision score.

### 5.5 Formulas and display units

The formulas below are design math, not claims that the current route already returns the deltas.

#### Volatility and candidate risk

With annual covariance `Σ = 252 × sample_covariance(daily_returns, ddof=1)`:

```text
σ_before = sqrt(w_before' Σ w_before)
σ_after  = sqrt(w_after'  Σ w_after)
Δσ       = σ_after - σ_before
candidate_variance_contribution = w_after[X] * (Σ w_after)[X]
candidate_RC% = candidate_variance_contribution / σ_after²
```

The response should also return candidate MRC or a documented derivative. A negative covariance contribution can lower portfolio volatility even when the candidate’s standalone volatility is high; the UI should say “diversifier” only when the server returns a computed result and the policy permits it.

#### Historical VaR/CVaR and MDD

Use one aligned return path and disclose loss sign:

```text
VaR_95  = -quantile_5%(R_p)             # display as positive loss fraction
CVaR_95 = -mean(R_p | R_p <= quantile_5%(R_p))
wealth_t = Π(1 + R_p,t)
MDD = min_t(wealth_t / running_peak_t - 1)  # signed negative fraction
```

The before/after paths use the same dates and no invented rebalancing. A drawdown result is an observed historical-path statistic, not a prediction. If there are too few tail observations, return `null` with a reason.

#### Concentration and exposures

```text
HHI       = Σ_i w_i²
N_eff     = 1 / HHI
sector_g  = Σ_{i in sector g} w_i
region_k  = Σ_{i in region k} w_i
sector_HHI = Σ_g sector_g²
region_HHI = Σ_k region_k²
```

`UNKNOWN` is a visible bucket. It cannot be silently assigned to a favorable sector. The current implementation already has the true HHI/effective-N formulas and the single-holding score rule (`backend/app/services/analytics_engine.py:239-249`).

#### Correlation

```text
rho(X, i) = Pearson correlation of aligned daily base-currency returns
rho(X, P_before) = correlation(X, current weighted portfolio returns)
rho(X, P_after)  = correlation(X, hypothetical weighted portfolio returns)
```

Return observation count and window for each. A high linear correlation does not replace a lower-tail dependence matrix; the existing tail matrix is a separate diagnostic (`backend/app/services/tail_risk_service.py:430-434` in the current schema and `backend/app/api/analytics.py:2419-2435`).

#### Tracking error

This is intentionally not faked in the first release:

```text
TE = sqrt(252) * sample_std_ddof1(R_portfolio - R_benchmark)
```

The current benchmark service is NIFTY-only and price-return based (`backend/app/services/benchmark_service.py:20-24`, `:89-136`). A new benchmark policy must return the benchmark symbol/rule, base currency, overlap sessions, and whether it is price-return or total-return. Until then the impact card is `Unavailable — no approved benchmark rule`, and the first-release verdict policy does not silently gate on TE.

#### Expected-return model

Name the model exactly in every response:

```text
trailing_252_session_arithmetic_mean
μ̂_p = 252 × mean(daily base-currency portfolio returns)
```

This is a **descriptive trailing model**, not a forecast, consensus estimate, DCF, or promise of future return. The current engine uses the same arithmetic annualization (`backend/app/services/analytics_engine.py:904-917`) and the optimizer exposes the same convention (`backend/app/services/optimization_service.py:39-43`, `:320-328`). The response must return the risk-free rate used or `null`; the static 2% backend default (`backend/app/config.py:53`) must be disclosed if used, never hidden in the client.

#### Liquidity

```text
ADV_shares = mean(positive daily volume over 30 sessions)
ADV_base   = mean(raw close × positive daily volume over 30 sessions)
quantity   = proposed amount / current quote
%ADV       = 100 × quantity / ADV_shares
%ADV_value = 100 × proposed amount / ADV_base
days(p)    = proposed amount / (p × ADV_base)
```

Show 5%, 10%, and 20% participation as sensitivity; the first gate can use 10%. This is a participation estimate, not an order-book, spread, slippage, or execution forecast. The current measured service returns `null` when ADV is unavailable (`backend/app/services/india_data_service.py:357-411`); preserve that behavior.

## 6. Live-data verdict: IMPROVES / NEUTRAL / DISADVANTAGES

### 6.1 Authority

The **backend** should compute the verdict and decision gates as part of the proposed read-only impact response. The frontend renders the returned status and evidence. It must not independently subtract two unrelated endpoint values, guess a sign, or fill a missing metric.

The verdict is a portfolio-fit classification, not investment advice and not a buy/sell order.

### 6.2 Proposed Balanced policy preset

These are explicit product-policy defaults requested by this design; they are not current backend outputs. They must be versioned, returned in the response, and configurable by the user. If no approved policy is configured, use `UNAVAILABLE`, not a hidden default.

| Policy gate | Proposed threshold | Unit/interpretation |
|---|---:|---|
| Maximum post-add position weight | `0.15` | 15% of risky portfolio value; user may choose another preset. |
| Maximum post-add sector weight | `0.30` | 30%; `UNKNOWN` counts against classification coverage. |
| Maximum post-add listing-region weight | `0.50` | 50%; useful for IN/US mixes. |
| Maximum positive sector drift | `5.0` percentage points | Candidate may increase a sector by no more than 5 pp under the balanced preset. |
| Maximum positive region drift | `10.0` percentage points | Candidate may increase a listing region by no more than 10 pp. |
| Maximum absolute candidate-to-holding correlation | `0.70` | A candidate above this is a concentration warning, not a standalone recommendation. |
| Maximum proposed position as % ADV | `10%` | Applies to both shares and base-currency value where available. |
| Maximum liquidation days at 10% ADV | `5 trading days` | Capacity check, not an execution promise. |
| Maximum positive Δ annualized volatility | `+1.0` percentage point | Above this is material harm. |
| Maximum positive Δ historical VaR | `+0.50` percentage point | Above this is material harm. |
| Maximum positive Δ historical CVaR | `+0.50` percentage point | Above this is material harm. |
| Maximum positive Δ historical MDD | `+1.0` percentage point | Above this is material harm. |
| Maximum positive Δ HHI | `+0.02` | Above this is material concentration harm. |
| Supporting expected-return improvement | `+0.50` percentage point | A supporting signal only; never enough by itself to produce IMPROVES. |
| Supporting effective-N improvement | `+0.10` positions | A supporting signal only. |

The proposed service should return the exact `policy_version` and each gate’s `value`, `threshold`, `operator`, and `status`. The user should be able to see why a verdict changed after changing size.

### 6.3 Classification algorithm

1. **Data gate first.** If identity, amount/funding, currency, price history, aligned sessions, covariance, or a required liquidity leg fails, return `verdict.status = "unavailable"` with reason codes. Do not call it NEUTRAL.
2. **Hard-gate check.** Any failed position, sector, region, correlation, or liquidity limit produces `DISADVANTAGES` for the configured policy. This is a constraint failure, not a claim that the security is intrinsically bad.
3. **Improvement count.** With all required data complete and no hard-gate failure, count the following server-evaluated benefits:
   - Δ volatility ≤ `−1.0 pp`;
   - Δ CVaR ≤ `−0.5 pp` (VaR may corroborate);
   - Δ MDD ≤ `−1.0 pp`;
   - Δ HHI ≤ `−0.02` **and** Δ effective N ≥ `+0.10`;
   - sector and region drift are non-positive or below their policy caps;
   - expected-return delta ≥ `+0.5 pp` when the named model is available.
4. **Harm count.** Count material violations of the corresponding risk/concentration thresholds, plus adverse sector/region drift, candidate correlation above `0.70`, and liquidity above the policy cap.
5. **Result:**
   - `IMPROVES`: all required data present, no hard-gate failure, no material harm, and at least two independent benefit signals. Expected return alone cannot satisfy this.
   - `DISADVANTAGES`: any hard-gate failure or at least two independent material harm signals.
   - `NEUTRAL`: all required data present, no hard-gate failure, but fewer than two benefit signals and fewer than two harm signals.
   - `UNAVAILABLE`: required data or policy is missing; this is a distinct state, not a hidden neutral result.

The response should return the reason codes and the input values behind the label. A single metric card must never display a bare “IMPROVES” badge.

### 6.4 Empty-portfolio exception

For the first holding:

- use `NEUTRAL` with reason `empty_portfolio_bootstrap`, not a comparative quality judgment;
- show post-add weight `100.00%`, HHI `1.0`, effective N `1.0`, and diversification score `0%`;
- do not apply the comparative 15% position cap, because the policy is explicitly bootstrapping;
- still require valid identity, quote freshness, supported currency, and liquidity;
- explain “There is no prior portfolio to improve or worsen.”

This preserves the AGENTS.md zero-state invariant and prevents a fabricated portfolio total from creating a false comparison.

### 6.5 Optional data versus required data

- **Required for a verdict:** identity/quote, funding/weights, common return window, volatility, VaR/CVaR, MDD, HHI/effective N, exposure classification for the configured gates, and amount-aware liquidity.
- **Supporting/context only:** fundamentals, valuation ratios, technicals, ownership, insider activity, expected return when the risk-free rate is unavailable, and tracking error until a benchmark policy exists.
- **Never silently substituted:** news/sentiment, analyst target, forward EPS, or a DCF. The current route inventory has no such fields.

## 7. Step 4 — Size, review, and add

### 7.1 Size control

Preferred first-release input is **amount in the selected base currency**. A target-weight input may be an alternate view, but the server must receive an explicit amount/funding basis; it must not infer cash from a stored weight.

Required labels:

- `Amount to add` with currency;
- `Estimated quantity` from the server quote;
- `Funding: external cash (hypothetical)`;
- `Analysis window` and `as of`;
- `Recalculate` button and last successful calculation time.

Do not recompute the verdict silently on every keystroke. Use a short debounce or explicit recalculation, cancel stale requests, and invalidate the review whenever amount, currency, ticker, quote, or policy changes. A pending calculation must keep the previous result visibly marked **Updating** or clear it; it must never show an old result beside a new amount.

The current backend create schema accepts `weight`, `quantity`, `buy_price`, `region`, and optional name/date (`backend/app/models/schemas.py:11-19`; frontend type at `frontend/src/types/index.ts:165-173`). It does not accept `amount` or a funding mode. Therefore the amount-to-quantty/weight translation is a proposed backend/frontend contract seam, not a current capability.

### 7.2 Review panel

The review is a right-side drawer on desktop and a full-width section on mobile. It contains:

1. **Identity and quote:** ticker, company, exchange, currency, quote source, quote/bar as-of, freshness.
2. **Trade intent:** amount, estimated quantity, entry-price field, purchase date, funding mode, current portfolio value.
3. **Resulting weights:** current weight, candidate post weight, every changed holding weight, and reconciliation status.
4. **Impact table:** before → after and delta for volatility, VaR, CVaR, MDD, HHI, effective N, diversification, largest position, sector/region drift, candidate correlation, tracking error, expected return, ADV, %ADV, and liquidation days.
5. **Verdict:** status, policy version, hard gates, reason codes, and “what would change the verdict.”
6. **Data quality:** sources, periods, aligned sessions, freshness, fallback FX/provider, and unavailable fields.
7. **Commit action:** `Add to portfolio` only after a successful server review.

Use a table or definition list for before/after values; do not encode direction in color alone. A negative MDD, positive loss VaR, and negative return need explicit unit labels.

### 7.3 Confirmation semantics

The primary action is a normal button in the review panel, not a new modal. Use a confirmation dialog only if the action is ambiguous or destructive. Existing Radix primitives are available and already provide portal, focus management, Escape, and body scroll lock (`frontend/src/components/ui/dialog.tsx:49-99`), so no new dependency is needed.

On confirm:

1. Disable the button and show an in-flight label; prevent double submit.
2. Call the existing `POST /api/v1/portfolio/add` with the server-reviewed `ticker`, `quantity`, `buy_price`, `weight`, `region`, and optional `custom_name`/`added_on`.
3. Treat the response as the mutation receipt. The backend route refetches the quote, validates the duplicate, commits, and returns `PortfolioPositionResponse` (`backend/app/api/portfolio.py:335-456`).
4. On success, refetch `GET /portfolio` and show the server-returned position/total. The existing API wrapper and refresh pattern are at `frontend/src/lib/api.ts:130-148` and `:129-143` in the store.
5. If the row committed but the post-commit response refresh fails, show “Position saved; portfolio summary could not be refreshed” and offer a read-only retry. The backend explicitly distinguishes a durable commit from a failed response (`backend/app/api/portfolio.py:427-464`).
6. On 409, show “Already held” and route to the existing position/update view; do not retry automatically.
7. On 422, show field-level validation beside quantity/price/date. On 503, show provider degradation and a retry; do not replace the quote with a stale screener price.
8. Never mark `Added` before the server response. The current quick-add state flips to an “Added” badge after its request (`screener-studio/page.tsx:163-199`); the flagship review should be stricter.

The current store action catches and stores errors rather than always rethrowing (`frontend/src/lib/store.ts:126-147`). The future add flow should use an API method that preserves the `AppError` status/detail and make the caller distinguish success from failure; a successful-looking UI must not depend on a swallowed rejection.

### 7.4 Purchase-price semantics

The current add route stores the submitted `buy_price` while separately refreshing `last_price` (`backend/app/api/portfolio.py:393-409`). The review must label these separately:

- **Entry price / buy price** — the user’s recorded transaction price;
- **Current quote** — the latest vendor/cache price used for current value and impact;
- **As-of** — when each was observed.

Do not silently replace a user’s entry price with the current quote, and do not infer a buy date or lot size that the backend has not supplied.

## 8. State machine

States are explicit. Freshness, provider degradation, and partial data are orthogonal flags where useful, but they still affect which actions are enabled.

```text
BOOT
  └─ DISCOVERING
       ├─ SCREEN_READY
       ├─ DIRECT_QUERY
       └─ ERROR_PROVIDER
              ↓
        VALIDATING_IDENTITY
          ├─ NO_RESULT
          ├─ INVALID_TICKER
          ├─ ALREADY_HELD
          └─ IDENTITY_READY
                 ↓
             RESEARCH_LOADING
              ├─ RESEARCH_PARTIAL
              ├─ RESEARCH_READY
              ├─ STALE_PRICE
              ├─ PROVIDER_DEGRADED
              └─ RESEARCH_UNAVAILABLE
                     ↓
                 IMPACT_IDLE
                     ↓ (amount/policy valid)
                 IMPACT_LOADING
              ├─ IMPACT_PARTIAL
              ├─ IMPACT_UNAVAILABLE
              └─ IMPACT_READY
                     ↓
                 REVIEW_READY
                     ├─ AMOUNT_CHANGED → IMPACT_LOADING
                     ├─ QUOTE_CHANGED → IMPACT_LOADING
                     └─ ADD_SUBMITTING
                          ├─ ADD_CONFIRMED
                          ├─ ADD_FAILED_RETRYABLE
                          └─ ADD_FAILED_TERMINAL
```

### 8.1 Transition rules

| From | Event | To | Required behavior |
|---|---|---|---|
| Any ticker state | New ticker selected | `VALIDATING_IDENTITY` | Increment request sequence/abort old requests; clear old profile, chart, ownership, and impact data. |
| `VALIDATING_IDENTITY` | 404/unknown | `NO_RESULT` | Keep query; no previous-company content. |
| `IDENTITY_READY` | Research request fan-out | `RESEARCH_LOADING` | Show skeleton regions; do not block optional ownership on profile success. |
| `RESEARCH_LOADING` | One optional source fails | `RESEARCH_PARTIAL` | Show that card as unavailable with retry; keep other cards. |
| `RESEARCH_LOADING` | Profile/quote fails | `RESEARCH_UNAVAILABLE` | Show error; no synthetic identity card. |
| `RESEARCH_READY` | User enters valid amount | `IMPACT_LOADING` | Send explicit amount/funding/base currency/window/policy. |
| `IMPACT_LOADING` | Required leg missing/insufficient | `IMPACT_UNAVAILABLE` | Withhold verdict and add-review eligibility. |
| `IMPACT_READY` | Any amount/quote/policy change | `IMPACT_LOADING` | Invalidate old verdict; do not retain stale deltas. |
| `REVIEW_READY` | Confirm | `ADD_SUBMITTING` | Disable duplicate actions; retain review for error recovery. |
| `ADD_SUBMITTING` | 2xx response | `ADD_CONFIRMED` | Show server receipt and refreshed portfolio. |
| `ADD_SUBMITTING` | 409 | `ALREADY_HELD` | Stop; link to update/top-up path. |
| `ADD_SUBMITTING` | 422/503/500 | `ADD_FAILED_*` | Preserve exact server detail; distinguish retryable provider failure from terminal validation. |

### 8.2 Required state copy

| State | Headline | Supporting copy | Action |
|---|---|---|---|
| No result | No listed ticker found | “Check the exchange suffix or try another symbol.” | Edit query / open screener |
| Stale price | Price data is stale | “Latest bar is older than the permitted freshness window; refresh before assessing impact.” | Refresh / inspect history |
| Provider degraded | Using a fallback provider | “Some fields came from a fallback source; provenance and affected metrics are marked.” | Retry / review partial data |
| Insufficient history | Not enough aligned history for this decision | “Research facts may be available, but annualized covariance and the verdict are unavailable.” | Extend window only if backend supports it / view raw history |
| Unsupported currency | Currency cannot be compared safely | “This portfolio currently supports INR and USD; no unsupported FX conversion was applied.” | Choose supported base / leave research local-only |
| Partial data | Some research sections are unavailable | “Missing fields are not treated as zero and do not contribute to the verdict.” | Retry affected source / continue with impact if gates are complete |
| Already held | Ticker is already in the portfolio | “This is a top-up/update, not a new position.” | Open existing position / define top-up impact |
| Empty portfolio | Starting a portfolio | “There is no prior book to compare; the first holding is 100.00% by definition.” | Continue to size/review |

### 8.3 Freshness and fallback policy

- **Quote freshness:** the current portfolio refreshes prices older than 15 minutes (`backend/app/api/portfolio.py:1290-1297`). The new response should expose quote age and use the same policy as a default refresh trigger, while distinguishing a generated timestamp from a vendor timestamp.
- **OHLCV freshness:** use the existing technical guard of 10 calendar days (`backend/app/services/indicators_service.py:28-30`, `:97-114`) as the initial stale bar rule. A stale frame may remain visible as historical context but cannot feed a current verdict.
- **Provider degradation:** the cascade can move from configured bfinance/yfinance to another tier (`backend/app/services/source_preference_service.py:1-11`, `:88-92`; `backend/app/services/data_service.py:760-799`). The UI must show `source_used`, `fallback_used`, and affected fields. An Alpha Vantage fallback is not automatically equivalent to an adjusted-price source for long-horizon risk.
- **Partial data:** per-field/per-source status, not one global boolean. A missing ownership series must not erase a valid quote; a missing candidate return leg must block impact.

### 9.2 Existing mutation contract to reuse

The final mutation remains the current schema/route:

```text
POST /api/v1/portfolio/add
{
  "ticker": "...",
  "weight": 0.0,
  "quantity": 0.0,
  "buy_price": 0.0,
  "region": "IN | US",
  "custom_name": "...",
```

The backend validates positive weight/quantity/buy price (`backend/app/models/schemas.py:11-53`), validates the ticker, fetches a quote, rejects duplicates, persists, and returns a position response (`backend/app/api/portfolio.py:335-456`). The new impact response must be reviewable independently of this mutation.

### 9.3 Existing frontend contract gaps to resolve in implementation

- `StockData` is an item type (`frontend/src/types/index.ts:30-40`), but `dataApi.getStockData` says the route returns an array while the backend returns a timeseries envelope (`backend/app/models/schemas.py:127-137`; `frontend/src/lib/api.ts:235-242`). Define an envelope type and preserve source/cache metadata.
- `EquityResearchProfile` marks several custom ratios as required numbers (`frontend/src/types/index.ts:521-529`) even though the page already has to handle missing Piotroski values. Make nullable fields explicit in the new research contract.

- The API client has no technical, verified-snapshot, impact, or benchmark/TE methods. Add typed methods only when their backend contracts exist.
- Preserve `AppError.status` and `detail` (`frontend/src/lib/api.ts:44-112`) so 404, 409, 422, and 503 can drive distinct states.

## 10. Accessibility, responsive behavior, and interaction details

### 10.1 Keyboard and semantics

- Use a real `role="tablist"`/`role="tab"`/`role="tabpanel"` pattern for the research questions, with arrow-key navigation, `aria-selected`, `aria-controls`, and a visible focus ring. The current research tabs are plain buttons (`equity-research/page.tsx:550-580`); the target should not copy that limitation.
- Every search, amount, quantity, date, currency, and policy control has a persistent `<label>` and `htmlFor`/`id` association. Use `inputMode="decimal"` for amounts and announce the currency in the label/help text.
- The review drawer is a labelled dialog/drawer only when it behaves as one. Reuse the installed Radix wrapper; it already provides portal, focus trap, Escape, and scroll lock (`frontend/src/components/ui/dialog.tsx:49-99`).
- Do not close an in-progress or filled review on an accidental outside click. The current wrapper already supports `closeOnOutsideClick={false}` (`dialog.tsx:49-55`).
- On ticker change, move focus to the new candidate heading or announce “Research loaded for {ticker}”; do not leave focus on a removed row.
- Sortable research/peer tables use real buttons in headers and `aria-sort`; the existing portfolio table already demonstrates this pattern (`frontend/src/components/portfolio/PortfolioTable.tsx:64-89`).

### 10.2 Status announcements

- First-load skeletons carry `aria-busy="true"`; loading text describes the operation.
- Provider degradation, partial data, and stale bars use `role="status"`/`aria-live="polite"`.
- Validation errors and terminal add failures use `role="alert"` and are associated with the affected field.
- The verdict summary has a short screen-reader sentence: “Portfolio verdict: Disadvantages. Reason: proposed position exceeds the 10 percent ADV limit.” The full metric table remains available to assistive technology.
- Color is never the only signal: every up/down/risk state has text, an icon, and a numeric value. Use a checked color-blind-safe pair in the shared design system, not red/green alone.

### 10.3 Charts and dense data

- Every chart has a heading, as-of/source caption, keyboard-reachable data summary, and a table fallback for the key values.
- Price history uses a line/area chart for adjusted close plus a separate volume plot; do not encode six unrelated research APIs in one overloaded chart.
- Correlation uses a labeled matrix/table; the existing response contract returns `{tickers, matrix}` (`backend/app/models/schemas.py:430-434`), so bind `tickers` as headers and index `matrix[i][j]` rather than iterating the outer object.
- Wide peer/ownership/financial tables scroll horizontally with a sticky first column; mobile never shrinks text below readable size.
- The impact panel is dense but scan-first: verdict, candidate amount, hard failures, then expandable evidence.

### 10.4 Motion and focus

- Use short state transitions only: skeleton → content, pending → success/error, amount → recalculating. No page-load choreography.
- Respect reduced-motion settings.
- After successful add, move focus to a receipt heading; after failure, keep focus on the error summary and provide a retry button.

## 11. Handoff boundaries and implementation order

### Backend owns

1. Canonical ticker identity and listing/currency resolution.
2. One common price/return/FX/calendar window and explicit source/as-of/provenance.
3. The funding resolver and post-weight vector.
4. All quantitative before/after calculations, including HHI/effective N, correlation, VaR/CVaR/MDD, exposures, expected-return model, and amount-aware liquidity.
5. The policy preset, gate evaluation, and authoritative verdict.
6. Read-only behavior for the impact request; no portfolio mutation.
7. A clear error taxonomy for 404, 409, 422, 503, insufficient history, stale data, and unsupported currency.

Likely backend seams for a future implementation are `backend/app/api/analytics.py`, a new orchestration service, `backend/app/models/schemas.py`, and possibly the benchmark/currency services. None of those files are changed by this report.

### Frontend owns

1. URL/deep-link state and request orchestration.
2. Loading, stale, provider-degraded, partial, no-result, and error presentation.
3. Rendering the server-returned values/statuses and policy reasons.
4. Amount input invalidation, review focus, keyboard/accessibility, responsive layout, and mutation confirmation.
5. Refetching the portfolio after a successful add and displaying the server receipt.

The frontend must not own quantitative formulas, infer missing provider fields, or convert an unavailable value to a neutral/zero state.

### Product/data owner must approve

- The Balanced policy preset and its versioning.
- Whether the first release uses external cash only.
- The benchmark policy for tracking error (NIFTY, S&P 500, or a disclosed mixed-region rule).
- Whether US ownership/estimates are required before the journey can be called global.
- The semantic definition of “region” (listing/exchange region, not issuer domicile or revenue geography).

### Suggested delivery slices

1. **Contract slice:** freeze the proposed impact request/response, null/status semantics, funding mode, and policy gate schema. Add backend tests for empty portfolio, duplicate ticker, unsupported currency, stale bar, provider fallback, insufficient history, and exact null propagation.
2. **Research slice:** align frontend types with current quote/timeseries/technical contracts; add per-source status cards, stale/degraded banners, and price-history/technical sections. No new dependencies.
3. **Impact slice:** implement the read-only backend orchestration, then add the decision rail and size/recalculation flow. Do not wire the add button to impact placeholders.
4. **Mutation slice:** connect the review to the existing add route, preserve server errors, and add server-confirmation/reconciliation tests.
5. **Benchmark/advanced slice:** add TE with an explicit benchmark policy; then consider US ownership, news, estimates, and mixed-region stress/regime views as separately sourced capabilities.

### Acceptance gates

- No direct screener-to-create mutation without a review.
- No metric delta is rendered unless its `delta` is finite in the current response.
- No previous ticker’s data remains visible after a failed switch.
- A stale or unsupported-currency impact cannot produce a normal verdict.
- A provider fallback is labeled and never presented as a clean primary feed.
- First position is 100.00% only after a successful empty-portfolio read; a failed portfolio read blocks add.
- HHI/effective N use true weights; one holding displays 0% diversification score.
- Tracking error is visibly unavailable until a benchmark rule exists.
- The add success state is based on the server’s position response and a refreshed portfolio, not a local `Added` flag.
- All keyboard, screen-reader, and mobile paths have a real focusable control and no color-only meaning.

## 12. Top 3 highest-leverage design changes

1. **Replace the direct one-share screener add with a server-backed, amount-aware before/after review.** This is the single change that makes the product’s “not on free sites” advantage visible: the user sees risk, concentration, exposure, and capacity together before committing.
2. **Make provenance and nullability a first-class product language.** Freshness, source, period, fallback, and missingness must be visible in every research and impact card; this prevents stale values, provider outages, and fake zeros from becoming quiet financial advice.
3. **Move the verdict and threshold policy to the backend contract.** A server-owned `IMPROVES / NEUTRAL / DISADVANTAGES / UNAVAILABLE` result with explicit gates is the only trustworthy way to keep the flagship flow coherent across screeners, research, sizing, and confirmation.

## 13. Non-goals and explicit omissions

- No DCF, target price, consensus return, sentiment score, or order-book spread claim.
- No new charting, state-management, or UI dependency; reuse the installed Radix, Axios, Recharts, Lucide, TanStack, and existing UI primitives.
- No new cash ledger in the first slice; external cash is explicitly hypothetical.
- No pro-rata or targeted selling mode until the backend can resolve and reconcile named funding amounts.
- No automatic trade execution, tax, brokerage, or portfolio rebalancing as part of the add action.
- No new backend endpoint is presented as current; only the proposed impact contract is marked as new work.
